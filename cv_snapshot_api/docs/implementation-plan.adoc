= 현재 프레임 OpenCV API 구현 계획
:toc:
:toclevels: 3

== 목표

`cv_snapshot_api`에서 레퍼런스와 동일한 외부 API를 유지하면서 지정 포트로 이미지
요청을 받으면 현재 카메라 프레임을 획득하고 OpenCV 처리 후 JPEG로 반환한다.

[source,text]
----
POST /opensdk/{app_id}/startserver
GET  http://{camera-ip}:{port}/image/jpg
----

`app/html/index.html`은 같은 API를 호출하는 테스트용 웹 클라이언트로 사용한다.

== 레퍼런스 원칙

* `snapshot_jpeg`에서는 현재 프레임 JPEG 획득 흐름만 참고한다.
* `display_image_opencv`에서는 포트 서버, 테스트 웹, OpenCV 처리와 HTTP JPEG 응답
  흐름만 참고한다.
* 두 레퍼런스에는 파일 추가를 포함해 어떠한 변경도 하지 않는다.
* 실제 구현과 실험은 `cv_snapshot_api`에서만 수행한다.

== 초기 영상처리

[source,text]
----
현재 프레임 JPEG 획득
→ grayscale decode
→ GaussianBlur(Size(3, 3))
→ Canny(100, 200)
→ JPEG encode
→ HTTP image/jpeg response
----

영상처리는 네트워크 및 SDK 이벤트 코드와 분리해 이후 알고리즘과 파라미터를 교체할
수 있게 한다.

== 단계별 계획

[cols="1,2,5"]
|===
|단계 |상태 |내용

|0. 분석 및 계획
|완료
|프로젝트 역할, 기존 endpoint, SDK 이벤트, 변경 금지 범위와 개발 기록 방식을
문서화한다.

|1. OpenCV 및 CMake 적용
|완료
|CV5 ARM64 OpenCV를 `app/3rd_party`에 병합하고 component include, link, install
규칙을 추가한다.

|2. AppNetworkManager 구성
|완료
|`app/src/CMakeLists.txt`, LifeCycle manifest와 instance manifest에 NetworkManager
runtime, scheduler, receiver와 source를 추가한다.

|3. `/startserver` 구현
|완료
|레퍼런스 endpoint, 포트 JSON 파싱, 범위 검증, 서버 시작과 HTTP 상태 응답을
구현한다.

|4. `GET /image/jpg` 파싱
|완료
|클라이언트별 수신 버퍼를 관리하고 `eServerData`에서 method/path와 HTTP 헤더
종료를 검사한다.

|5. 현재 프레임 캡처
|완료
|AppInfo로 app ID를 확보하고 `eAppSnapshotJpeg`로 요청 시점 프레임을 저장한다. 현재는 `res` 쓰기 조건 확인을
위해 `../res/capture.jpg`를 사용한다.

|6. OpenCV 처리 분리
|완료
|`FrameProcessor`와 처리 옵션 모델을 추가하고 초기 Canny 파이프라인을 구현한다.

|7. JPEG HTTP 응답
|완료
|정확한 Content-Length, Content-Type, 오류 상태와 JPEG binary 전송을 구현한다.

|8. 테스트 웹
|완료
|포트 서버, snapshot, OpenCV 처리, 전체 API를 각각 실행하는 진단 버튼으로 고장
구간을 분리하고 결과를 표시한다.

|9. Docker 빌드 및 CAP
|완료
|`cv_snapshot_api`만 대상으로 Docker 빌드, install, dependency 검사와 CAP 생성을
수행한다.

|10. 카메라 런타임 검증
|완료
|실제 카메라에서 서버 시작, JPEG API, 테스트 웹, 오류 처리, 응답시간과 반복 요청
안정성을 검증한다.
|===

== 초기 설정

[source,json]
----
{
  "jpeg_path": "../res/capture.jpg",
  "processed_jpeg_path": "../res/processed.jpg",
  "processing_mode": "canny",
  "blur_kernel_size": 3,
  "canny_low_threshold": 100,
  "canny_high_threshold": 200,
  "jpeg_quality": 90
}
----

포트는 레퍼런스와 동일하게 `/startserver`에서 전달한다. 영구 저장과 앱 시작 시 자동
실행은 이번 범위에 포함하지 않는다.

== 검증 기준

. 레퍼런스 두 프로젝트 파일이 변경되지 않아야 한다.
. OpenCV 라이브러리가 ELF 64-bit ARM aarch64여야 한다.
. component 빌드, OpenCV 링크와 install이 성공해야 한다.
. install 및 CAP에 component와 OpenCV runtime이 포함되어야 한다.
. 실제 카메라에서 `/startserver`와 `/image/jpg`가 동작해야 한다.
. 응답이 유효한 Canny 처리 JPEG여야 한다.
. 잘못된 포트, path, JSON과 캡처 실패가 적절한 오류를 반환해야 한다.

CAP 생성까지만 성공하고 카메라에서 실행하지 않은 상태는 런타임 완료로 간주하지
않는다.

== 보류 중인 결정

* 실행 중 포트 재설정 및 기존 서버 종료 정책
* HTTP 인증과 외부 접근 제한
* HTTPS 지원 여부
* 동시 요청 수와 busy 응답 정책
* 처리 모드와 파라미터를 변경하는 외부 설정 API
== 단계별 진단 API 승인 및 구현 (2026-07-22)

사용자는 카메라에서 snapshot 파일이 생성되지 않고 전체 이미지 요청이 대기하는
구간을 분리하기 위해 `/capture`, `/process` 진단 endpoint와 별도 웹 버튼 추가를
승인했다. `/capture`는 snapshot만, `/process`는 기존 파일의 OpenCV 처리만 수행한다.
기존 `/startserver`와 `/image/jpg` 계약은 유지한다. 브라우저 요청에는 10초 timeout을
적용한다. CV5 빌드와 카메라 실행 전이므로 단계 5, 6, 8은 계속 `진행 중`이다.
== 현재 진행 상태 (2026-07-22)

단계 1~8의 소스, CMake, manifest, 기본 설정과 테스트 웹 구현을 적용했다. JSON,
JavaScript 문법과 포함된 OpenCV ELF 아키텍처는 정적으로 확인했다. 현재 Windows 작업
환경에는 Docker 및 CV5 SDK compiler가 없어 component 크로스 빌드, install, 새 CAP
생성과 카메라 실행은 미검증 상태다. 따라서 빌드 검증과 연결된 단계 1~9는 `진행 중`을
유지한다.
== Docker 1차 빌드 결과 (2026-07-22)

VirtualBox Linux의 CV5 Docker에서 CMake configure와 generate는 성공했다. 컴파일
33%에서 `CloseClient()`가 `SendNoReplyEvent(..., client_id, nullptr)`를 호출해
템플릿 인자 `T*`를 추론하지 못하는 오류가 발생했다. SDK가 제시한 payload 없는
3인자 overload에 맞춰 `SendNoReplyEvent(..., client_id)`로 수정했다. 재빌드 전이므로
단계 1~9는 계속 `진행 중`이다.
== 런타임 진단 로그 추가 (2026-07-22)

동작하지 않는 원격 `DebugLog` 대신 `stderr`와 즉시 flush를 사용하는 공통 `Trace()`를
추가했다. 초기화부터 서버 시작, HTTP 수신, snapshot, OpenCV, JPEG 응답 및 client
종료까지 단계별 INFO/ERROR 로그가 출력된다. 외부 API에는 변화가 없다. CV5 Docker
재빌드 전이므로 관련 단계 상태는 계속 `진행 중`이다.
== `res` 경로 쓰기 조건 실험 (2026-07-22)

사용자 결정에 따라 snapshot 기본값과 C++ fallback을 `../res/capture.jpg`로 변경했다.
OpenPlatform이 설치 앱의 `res`에 파일을 생성할 수 있는지 카메라에서 확인한다. 외부
API는 바뀌지 않는다. 기존 저장 Attribute가 기본값을 덮어쓸 수 있으므로 SNAPSHOT
요청 로그의 실제 path를 기준으로 판단한다. 실험 후 `storage` 복귀 여부를 결정한다.
== HTTP 진단 응답 및 테스트 웹 개선 (2026-07-22)

런타임 로그를 확인할 수 없는 환경을 위해 기존 endpoint의 오류 응답에 `success`,
`http_status`, `stage`, `error_code`, `message`를 추가했다. 이미지 API 오류는 JSON으로
반환한다. `FrameProcessor`는 옵션, decode, OpenCV, JPEG encode 오류 코드를 분리한다.
테스트 웹은 `fetch()`로 상태와 오류 JSON을 표시하고 성공한 JPEG만 화면에 렌더링한다.
endpoint 변경은 없다. CV5 Docker 재빌드와 카메라 응답 확인 전까지 관련 단계는
`진행 중`이다.
== 원본 표시 및 처리 결과 저장 (2026-07-22)

사용자 요청에 따라 `/capture` 성공 응답을 원본 JPEG로 변경해 테스트 웹에 현재 프레임을
표시한다. OpenCV로 encoding한 결과는 HTTP 응답뿐 아니라 기본
`../res/processed.jpg`에도 저장한다. `/process`와 전체 `/image/jpg` 흐름 모두 같은 저장
함수를 사용한다. Full API의 10초 timeout은 계속 진단 대상으로 두며, `/capture`와
`/process` 결과에 따라 snapshot과 AppNetworkManager 구간을 구분한다. CV5 빌드와
카메라 검증 전이므로 단계 5~8과 10은 `진행 중` 상태다.
== 버튼별 API 정보 표시 (2026-07-23)

사용자 요청에 따라 테스트 웹의 각 버튼 오른쪽에 Method, 실제 endpoint, 요청 body와
응답 형식을 표시한다. 현재 페이지의 host와 APP_ID를 사용하고 포트 입력 변경 시
Start Server body와 Full API 주소를 실시간 갱신한다. JavaScript 문법은 정적으로
확인했으며 새 CAP 설치와 카메라 화면 확인 전이므로 단계 8은 `진행 중`이다.
== `../res/log` 파일 로그 관리 (2026-07-23)

사용자 결정에 따라 기존 stderr `Trace()`를 유지하면서
`../res/log/cv_snapshot_api.log`에도 같은 단계 로그를 기록한다. 별도 `FileLogger` 모듈이
디렉터리 생성, timestamp, mutex 직렬화와 1 MiB 기준 백업 3개 회전을 담당한다. 파일
기록 실패는 기능 실패로 전파하지 않는다. `std::mutex` 사용을 위해 component에
`pthread`를 명시적으로 링크한다. CV5 빌드와 카메라 경로·권한·회전 검증 전이므로 관련
빌드 및 런타임 단계는 `진행 중`이다.
== Full API `eClientData` 최소 수정 (2026-07-23)

카메라 로그에서 Full 요청이 `[CLIENT] connected` 이후 HTTP data 단계로 진행하지 않는
것이 확인됐다. 사용자 승인에 따라 `ProcessAEvent()`에서 `eClientData`도 기존
`HandleNetworkData()`로 전달하고, `eClientData`와 `eServerData` 이벤트 이름을 파일
로그에 남긴다. HTTP parser와 후속 snapshot/OpenCV 코드는 변경하지 않는다. SDK enum
존재와 case 연결은 정적으로 확인했으며 CV5 build와 runtime 재검증 전이므로 단계 4,
7, 9, 10은 `진행 중`이다.
== 정상 기준 이후 SampleComponent 파일 분리 (2026-07-23)

사용자가 `eClientData` 수정 CAP에서 Full 이미지 API 정상 호출을 확인한 상태를 분리 전
기준으로 삼는다. `SampleComponent` class는 유지하면서 core, network, image 멤버 정의를
각각 `sample_component.cc`, `sample_component_network.cc`,
`sample_component_image.cc`로 분리한다. 공통 free `Trace()`는
`FileLogger::Trace()`로 이동하고 JSON 응답 helper는 private member로 변경한다. API,
manifest, 처리 옵션과 다른 포트 요청의 HTTP 409 정책은 바꾸지 않는다. 정적 검사는
통과했으며 CV5 재빌드와 회귀 실행 전이므로 단계 3~10은 `진행 중`이다.

== 로그 관리 API 및 테스트 UI 묶음 구현 (2026-07-23)

CAP 재설치 횟수를 줄이기 위해 로그 조회·삭제 API와 테스트 웹 UI 개선을 한 변경으로
묶는다. 기존 Start, Capture, Process, Full API 계약과 포트 409 정책은 유지한다.

. `FileLogger`에 현재/백업 로그 tail 조회와 현재/전체 삭제를 추가한다.
. 고정 파일 이름, 최대 500줄, 최대 256 KiB로 입력과 읽기 범위를 제한한다.
. `GET /logs`와 확인 문자열이 필요한 `POST /logs/clear`를 등록한다.
. 테스트 웹에 로그 조회, 필터, 검색, 기본 OFF 5초 자동 갱신과 삭제 버튼을 추가한다.
. 기존 네 이미지 기능을 PC 진단 카드와 이미지 비교 영역으로 재배치한다.
. JavaScript·JSON·source/CMake 연결과 레퍼런스 해시를 정적으로 검사한다.
. clean CAP를 한 번 생성·설치한 뒤 모든 버튼을 순서대로 회귀 테스트한다.

소스와 정적 검사는 완료했지만 CV5 cross compile, CAP 재생성, 카메라 로그 파일 권한과
브라우저 실제 동작은 아직 미검증이므로 단계 9~10은 진행 중이다. 로그 삭제는 복구할 수
없는 동작이므로 웹 확인 대화상자와 서버 확인 문자열을 모두 통과해야 한다.
== CV5 CAP 및 카메라 최종 검증 완료 (2026-07-23)

사용자가 새 CAP 설치 후 구현 기능과 테스트 항목을 모두 확인했고 정상 동작한다고
보고했다. 이에 단계 1~10을 `완료`로 변경한다.

확인 완료 범위는 Start Server, Capture Frame, Process Image, Full API Test, 원본·처리
이미지 표시, 로그 조회·필터·검색, 현재/전체 로그 삭제, 자동 새로고침, 오류 조건과
동작 안정성이다. CPU와 thread의 구체적인 측정 수치는 제공되지 않았으므로 정상 여부만
기록하고 숫자는 추정하지 않는다.

실행 중 포트 변경, 인증·HTTPS, 동시 요청 성능 정책과 처리 파라미터 외부 설정은 기존
보류 항목으로 남으며 이번 구현 완료 판정에는 포함하지 않는다. 레퍼런스 프로젝트는
계속 읽기 전용으로 유지한다.
== Workflow 진단 콘솔 UI 개선 (2026-07-23)

기존 API와 카메라 처리 코드는 정상 기준선으로 유지하고 테스트 HTML만 개선한다.

[cols="1,2,5"]

=== UI 런타임 판정 수정 (2026-07-23)

카메라 테스트에서 Full API는 성공했지만 Capture가 `application/octet-stream`으로 반환돼
새 UI의 엄격한 Content-Type 검사에서 실패했다. 이는 Capture/Process가 JPEG를
`OpenAppResponseType::FILE`로 반환하는 AppDispatcher 계약에 따른 것이다.

* Capture/Process: `image/jpeg` 또는 `application/octet-stream`을 허용하되 JPEG SOI
  `FF D8 FF`를 필수 검사한다.
* Full: 직접 생성한 HTTP 응답의 `image/jpeg` 요구를 유지한다.
* JPEG가 아닌 성공 body는 `INVALID_JPEG_RESPONSE`로 거부한다.
* 사용자의 범위 결정에 따라 모바일 전용 media query를 제거하고 PC 웹만 지원한다.

정적·모의 응답 검증은 완료했지만 수정 CAP의 실제 Capture/Process 재확인 전이므로 UI-5는
`진행 중`을 유지한다.

== 단일 채널 다중 알고리즘 이미지 비교 계획 (2026-07-24)

=== 목표와 범위

CH 1~4 중 하나를 선택해 현재 프레임을 한 번만 캡처하고, 동일한 원본 `cv::Mat`에 여러
OpenCV 알고리즘을 독립 적용한다. 웹과 외부 클라이언트는 알고리즘별 JPEG를 GET하여
나란히 비교한다. 기존 `/image/jpg`와 4채널 개별·일괄 테스트는 유지하며, 알고리즘 비교
화면에서는 선택한 채널 하나만 사용한다.

알고리즘마다 프레임을 다시 캡처하지 않는다. 각 알고리즘은 동일 촬영 시점·해상도·원본에서
시작하고 다른 알고리즘의 출력을 입력으로 사용하지 않는다. 연속 처리 pipeline 비교는 향후
별도 기능으로 구분한다.

=== 예정 API와 결과

[source,text]
----
GET  /opensdk/{app_id}/processors
POST /opensdk/{app_id}/compare
GET  http://{camera-ip}:{port}/comparison/jpg
     ?run_id={run_id}&algorithm={algorithm}
----

`POST /compare` 요청 초안:

[source,json]
----
{
  "channel": 1,
  "algorithms": ["original", "grayscale", "blur", "canny"]
}
----

응답에는 `run_id`, 선택 채널, 알고리즘별 상태·처리시간·JPEG 크기·`image_url`을 포함한다.
여러 JPEG를 하나의 응답에 넣지 않고 각 URL을 개별 GET한다. 일부 알고리즘이 실패해도 다른
성공 결과는 유지한다.

결과 경로 초안:

[source,text]
----
../res/comparisons/{run_id}/
├── source_chN.jpg
├── original.jpg
├── grayscale.jpg
├── blur.jpg
├── canny.jpg
└── result.json
----

`res`는 진단용이며 장기 보존이 필요하면 운영 전에 `storage` 전환과 보존 기간을 결정한다.
초기 구현은 CV5 부하를 제한하기 위해 알고리즘을 순차 실행하고 JPEG decode는 한 번만 한다.

=== PC 비교 UI

채널 하나와 비교할 알고리즘들을 선택하고 `알고리즘 비교 실행`을 누른다. 결과는 채널 행렬이
아닌 알고리즘 카드 그리드로 표시한다. 각 카드에 이미지, 알고리즘 이름, 해상도, 처리시간,
JPEG 크기, 상태와 확대 기능을 표시하며 Original은 항상 포함한다. 기존 4채널 UI는 별도
진단 기능으로 유지한다.

=== 공통 접이식 로그 패널

로그는 별도 화면으로 분리하지 않고 기본 테스트, 알고리즘 비교와 4채널 진단 화면 오른쪽에
공통 `aside`로 유지한다. 펼친 상태는 약 380~440px, 접힌 상태는 약 44~56px 세로 레일로
표시한다. 접힌 레일에는 LOG, 새 로그 수와 ERROR 수만 표시하고 누르면 다시 펼친다.

펼친 패널에는 로그 파일·줄 수·level·stage·검색, 수동 새로고침, 자동 새로고침, 최신 로그
따라가기와 선택 행 상세를 배치한다. 현재/전체 로그 삭제는 공간과 오조작을 줄이기 위해
더보기 메뉴 안에 두고 기존 확인 절차를 유지한다.

로그 갱신 정책은 다음과 같다.

* 기능 API 실행이 끝나면 로그를 한 번 갱신한다.
* 패널을 펼치면 즉시 한 번 갱신한다.
* 자동 새로고침은 패널이 펼쳐져 있고 페이지가 보일 때만 5초마다 실행한다.
* 패널을 접으면 주기적 갱신을 중단하되 API 실행 후 새 로그·ERROR 개수는 갱신할 수 있다.
* 알고리즘 결과의 `관련 로그 보기`는 패널을 펼치고 해당 `run_id`를 검색 조건에 적용한다.

패널 열림 여부, 너비, 필터와 최신 로그 따라가기 상태는 `localStorage`에 보존한다. 자동
새로고침은 안전을 위해 새 페이지 진입 시 기본 OFF로 시작한다. URL hash는 기능 화면만
`#snapshot`, `#compare`, `#channels`로 구분하고 로그 패널은 모든 hash에서 유지한다.

=== 완료 기준과 미결정 사항

* 한 실행에서 선택 채널 snapshot은 한 번만 발생한다.
